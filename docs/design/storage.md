# 存储：两个库，不是一个

<a id="r106"></a>

## 一、结论

存储层拆成两个存储，各自拿现成轮子，**不造存储引擎**：

| 库 | 存什么 | 轮子 |
| --- | --- | --- |
| **数据库** | 结构化数据、笔记正文、元数据、索引、事件日志 | Python 标准库 `sqlite3` |
| **附件库** | 图片 / 视频 / 音频 / 附件本体 | 文件系统，按内容哈希命名 |

## 二、为什么必须是两个

把二进制塞进 SQL 数据库不是"能不能"的问题，是**性能拐点**问题。SQLite 官方量测过这个拐点（[Internal Versus External BLOBs in SQLite](https://www2.sqlite.org/matrix/intern-v-extern-blob.html)）：

> For BLOBs smaller than 100KB, reads are faster when the BLOBs are stored directly in the database file. For BLOBs larger than 100KB, reads from a separate file are faster.

即：**100KB 是阈值，不是"允许不允许"**。同页还给出 `page_size` 取 **8192 或 16384** 时大 BLOB I/O 最好。

所以规则是：

- **小于等于 100KB**：直接塞进数据库，一个事务搞定，简单；
- **大于 100KB**：只把 `hash` / `size` / `mime` / 相对路径记进数据库，本体落附件库。

小图标、头像、缩略图走前者；视频附件走后者。**这条线是工程口径，不是洁癖** —— 超过阈值还硬塞，会把数据库页面缓存挤爆。

## 三、数据库（路线 106）

**选 `sqlite3` 标准库，不引第三方驱动。** 已在本机 Python 3.14.8 / SQLite **3.53.1** 上逐项验证：

| 能力 | 状态 | 用途 |
| --- | --- | --- |
| `json_extract` / `json_valid` | ✅ 内置 | 结构化字段、灵活属性 |
| FTS5 虚拟表 + `MATCH` | ✅ 内置 | 全文检索的**机制**够用；但中文分词必须显式选（见下） |
| `threadsafety == 3` | ✅ | 序列化模式，跨线程可共享，配合 WAL |
| `enable_load_extension` | ✅ | 将来若要 `sqlite-vec` 做向量检索留口子（**现在不引**） |

> **更正：FTS5 默认分词器搜不到中文（2026-10-17 实测）。** 「FTS5 内置够用」对**英文**
> 成立，对**中文**不成立：默认分词器 `unicode61` 把没有空格的中文整段当成一个 token，
> 于是 `MATCH '中文检索'` 返回 **0 条** —— 不是慢，是搜不到。同一段中文实测：
>
> | 分词器 | `中文检索` | `测试中文` | `天气`（2 字） |
> | --- | --- | --- | --- |
> | `unicode61`（默认） | 0 | 0 | 0 |
> | `trigram` | 1 | 1 | 0 |
>
> 所以 **FTS 上线前必须先定中文分词口径**：`tokenize='trigram'` 加两字词回退，
> 或在 Python 侧把 CJK 预切成重叠 bigram 再喂 `unicode61`。**没定之前不建 FTS 表** ——
> 建了就是「装完才发现搜不到」。这条口径落在 [editor.md §二十二](editor.md) 的未决里。

落点口径：

- **一个 APP 实例一个库文件**，随用户数据目录走，用户可整体备份、整体搬走 —— 契合"数据归用户"（本项目本体决策）；
- `journal_mode = WAL`：读写不互相阻塞；
- `page_size = 8192`（默认 4096；8192 命中官方建议区间）；
- `foreign_keys = ON`（SQLite 默认关闭，必须显式开）；
- 表结构演进走**迁移链**，满足不变量 **I4**：一切持久化数据带 `version` 且注册 `migrate(from, to)`。链条**按 schema 分键** —— 两条 schema 都从版本 0 起步，共用一张版本表会互相撞号。

**为什么要内核里的 `storage` 这一层？** 因为不变量 **I3** 把内核钉成单向四层 `config → log → storage → bus`，`storage` 是**层**不是某个引擎。业务模块不该直接 `import sqlite3`，只经这一层拿句柄与事务原语 —— 换实现不牵动业务，也不破坏 I1。

## 四、附件库（路线 107）

<a id="r107"></a>

**纯文件系统，内容是地址。** 文件名 = 内容哈希（`sha256` 前若干位 + 后缀），天然去重：同一张图存两次只落一份。

- 数据库只存元数据行（`hash` / `size` / `mime` / 原名 / 引用计数），**不存本体**；
- 写入用"临时文件 → `fsync` → `os.replace`"原子落盘，避免半截文件；
- 目录按哈希前两位分桶（`ab/cd/abcdef…`），避免单目录塞几万个文件；
- **回收靠引用计数**，不做后台扫描：删除先减计数，归零才真删。

**落地（2026-10-16，路线 107）：** 口径落成
[`storage/attachments.py`](../../src/lurnia/core/storage/attachments.py)（元数据表是
`attachment`，kernel schema v2）。四处实现细节在这里写明，免得代码与本节各说各话：

| 点 | 口径 |
| --- | --- |
| 文件名里的哈希 | 用**完整** sha256，不是"前若干位"：截断会引入碰撞，省下的只是一个长文件名 |
| 删除顺序 | **先删本体、再删元数据行，同一事务内**。元数据是权威，绝不留一条指向不存在本体的行；反过来的话，删本体失败时计数已经归零，回退不了 |
| 行在、本体丢 | `put` 顺手把本体补回来（换机器、手删都会造成这种状态）；`get` 则显式报「本体缺失」，不静默给空 |
| 100KB 这条线 | 落成 `fits_in_database()` / `BLOB_THRESHOLD`，供上层决定塞库还是落附件库；附件库**不拒绝**小文件，选用哪边是调用方的判断 |

## 五、SQL 放文件，不放 Python

**DDL 一律写在 `.sql` 文件里，Python 只负责读和跑。** 内联进 Python 的直接后果不是"丑"，是**读不到**：不去翻代码就不知道表长什么样，也说不清它搁在哪；表一多必然写散。

**家必须在包内，不能在仓库根。** 这是本方案唯一真正会咬人的约束：

冻结打包（PyInstaller）**只收包内的东西**；仓库根的 `config/` 既不属于 `lurnia` 包、也不在任何 `--add-data` 目标里，成品里根本没有它。放 `config/` 就是"开发时能跑、装完就炸"。

```
成品（安装后的 APP）里能不能读到：
  src/lurnia/core/sql/**      → 在包内，能读到
  config/table.sql            → 不在包内，读不到  ← 这就是不能放仓根的原因
```

> **更正（2026-10-16）**：本节原先用 "`uv build --wheel` 后 `config/` 不在 wheel 里" 作为依据。**论证方式是错的** —— `uv build` 产出的是发 PyPI 用的 wheel，本项目不发 PyPI，wheel 不是 APP 产物。结论（必须放包内）不变，理由换成上面这条冻结打包的事实。见 [packaging.md](packaging.md)。

所以：

| | |
| --- | --- |
| 位置 | 内核 schema：`src/lurnia/core/sql/kernel/`；业务 schema：`src/lurnia/components/<组件名>/sql/<schema>/`（两者都在包内，走同一个加载器，见下） |
| 读取 | `importlib.resources`（不是 `Path(__file__)` / `sys.executable` 拼路径——冻结后它们指向临时解包目录，且 zip 里会失效） |
| 收紧 | `tests/test_ddl.py` 断言每个 `.sql` 都能经加载器读到，且源码树里没有仓根流浪 SQL |
| 命名 | `tables/`：一张表一个 `<表名>.sql`；`migrations/`：`NNNN` = 迁移目标版本，逐文件 +1 |

**谁的表放谁的包（2026-10-17 修订）。** 本节原先只写了「家必须在包内」，没说「在包内哪一处」——
结果业务 schema 会被顺手放进 `core/sql/`，于是**每加一张业务表都会在内核目录产生 diff**，
review 时读起来像内核变更。现在定死：

| 谁 | 放哪 | 为什么 |
| --- | --- | --- |
| 内核 schema（`kernel`） | `src/lurnia/core/sql/kernel/` | `event_log`（004）与 `attachment`（107）**本来就是内核层的表**，它们属于内核，放着不动 |
| 业务 schema | `src/lurnia/components/<组件名>/sql/<schema>/` | 组件的表与组件同生共死；加业务数据结构不再动内核目录 |

**不是仓根 `config/`。** `config/` 在包外，冻结打包只收包内的东西（本节上文），
而且 `tests/test_ddl.py::test_workspace_config_dir_is_not_the_ddl_home` 专门拦这件事——
放进去**当场红**，理由就写在那个测试的断言消息里。

**落地前提**（现在还没有业务 schema，所以这件事还没做）：

- `src/lurnia/core/ddl.py` 目前把 SQL 根写死成 `lurnia.core`（`PACKAGE`），要加一层
  「schema → 包」的解析；
- `script/audit.py` 的 `schema_drift_violations()` 只扫 `core/sql/*`，要一并扫组件根，
  否则新根下的 schema 会丢掉 I4 的「快照 vs 迁移链」一致性防线；
- `tests/test_ddl.py::test_ddl_lives_inside_the_package` 的断言口径要跟着改；
- `script/build_sidecar.py` **不用改**：它的数据文件发现根是 `src/lurnia`
  （`PACKAGE.rglob("*.sql")`），组件包天然被覆盖。

**一句话一条语句？不需要。** 切分交给标准库 `sqlite3.complete_statement`，它认得字符串字面量里的分号和 `BEGIN ... END` 触发器体，所以一个文件可以塞多张表，也不必把每个文件限成一条。**不引第三方 SQL 解析器。**

**逐条 `execute`，不用 `executescript`。** 后者会先隐式 COMMIT，把迁移从"一个事务"变成"半途留下"的可能，I4 的可重入性就没了。

**每个版本一个事务。** 0→1 成功、1→2 失败时停在 **1**——不是 0 也不是 2。这是**对的**：修好那个坏文件重跑会从 1 接着走，而不是重放已经落地的活。`tests/test_ddl.py` 锁住了这个行为。

`schema_meta` 是**引导表**：读版本号之前它就得存在，所以它是唯一允许留在 Python 里的 DDL。

## 六、事件日志落哪（配合不变量 I5）

不变量 **I5** 要求"状态变更先写事件日志，后落数据"。因为事件日志和数据**同库**，这条直接由 SQLite 事务保证：

```
BEGIN;
  INSERT INTO event_log (...)   -- 先写日志
  UPDATE note SET ...           -- 后落数据
COMMIT;                          -- 要么都成，要么都不成
```

崩溃后重启，日志里必然已有该事件 —— 这就是 I5 的 conformance 测试要验的东西。**附件库不参与这个事务**：本体先落盘拿到哈希，再写数据库元数据行；孤儿附件由引用计数回收。

## 七、OnCasket 已废弃（路线 005）

原路线 005「使用组件 OnCasket」自研存储引擎，**已废弃**，见 [1.x 开发路线图 §废弃附录 005](../roadmap/1.x-开发.md#附录-005)。理由：

- 该引擎无代码、无设计、仓库已删除，不可复现；
- 存储能力本身还在，由 106 / 107 用现成轮子承担。

按规范第 9 章，005 不入路线增量、不占版本分配，仅以废弃附录形式沿用原号。**注意区分**：死掉的是 OnCasket 这个**引擎选型**，不是内核的 `storage` **层**（I3）。

## 八、什么时候才真的需要改库（schema 稳定性）

目标：**加功能不该动数据库**。达到它靠的不是「迁移写得好」，而是把易变的东西挡在表结构之外。

| 规则 | 含义 |
| --- | --- |
| **表只增不改** | 不删列、不改列的语义。改名 = 新建 + 迁移 + 弃用三步走（[versioning.md](versioning.md) §三） |
| **易变的进 JSON，不进行/列** | 块属性、导入来的元数据、将来长出来的字段，全部落在 `doc` / `attrs` 这类 JSON 列里。`json_extract` / `json_valid` 是 SQLite 内置的（§三 已实测），不必为每个新字段加一列 |
| **权威与派生分开** | 权威 = 丢了回不来的（文档、批注、修订）；派生 = 能从权威重算的（FTS 索引、反链索引、引用计数）。派生表的结构改动**不算破坏性变更**：可以 DROP 重建，重建本身就是它的迁移 |
| **真要加列也走迁移** | `ALTER TABLE ADD COLUMN` 是 SQLite 的安全操作，但仍必须带迁移文件（I4），且迁移可重入（§五） |
| **启动不扫全库** | 「打开就要算一遍」是慢性死亡。查询走索引；派生数据在**写入时增量维护**，不在启动时全量重算 |

**为什么写进设计而不是留给实现。** 因为它约束的是**表怎么设计**：把 20 个字段平铺成列的表，
加第 21 个功能就得改库；把易变部分收进 JSON 列的表，加第 21 个功能只改代码。
前者是「三天两头改库」的根因，事后改代码补不回来。

## 九、明确不做的

| 不做 | 为什么 |
| --- | --- |
| 自研存储引擎 / 页格式 / GC | OnCasket 的教训；有轮子 |
| 把大二进制塞进数据库 | 超过 100KB 反而更慢 |
| 引入 ORM | 标准库 `sqlite3` 够用，少一层魔法 |
| 引入外部全文索引服务 | FTS5 内置，且外部服务破不变量 I9 |
| 引入 `sqlite-vec` 等扩展 | 现在没需求；`enable_load_extension` 留着 |
| 联网 / 起服务 / 拉进程 | 不变量 **I9**：一切对外动作由用户显式发起 |

## 十、验收

- 库能建、能迁移：同一份数据从版本 N 迁到 N+1，迁移可重入（I4）；坏文件重跑从**最后一个成功的版本**续走；
- **DDL 在包里**：每个 `.sql` 都能经 `importlib.resources` 读到并完成迁移，不依赖仓库任何文件（冻结打包后同样成立）；
- 大附件不落库：写入 > 100KB 的文件后，数据库体积基本不变，附件库出现哈希文件；
- 崩溃一致性：在 `COMMIT` 前杀进程，重启后事件日志里已有该事件（I5）；
- 全文检索走 FTS5，不引外部依赖；
- 跨模块只经 `storage` 层，业务模块零 `import sqlite3`（I1 / I3）。
