# 事件日志的轮转

<a id="r004"></a>

路线 004。口径承接 [bus.md §五](bus.md)（事件日志只落什么）与
[storage.md §六](storage.md)（日志与数据同库、同事务）。

## 一、结论

**轮转 = 归档后裁剪，不是直接删。** 旧的若干条事件先整段写进一个归档文件、
`fsync` 落盘，**然后**才允许从库里删行。

| | |
| --- | --- |
| 操作 | `rotate_event_log(db, archive_dir, keep=N)` |
| 保留量 | **最新的 N 条**（计数口径，不是时间口径） |
| 归档 | 一行一个事件封套的 JSONL，放 `<数据目录>/event-log/` |
| 触发 | **显式调用**，宿主在启动时接（路线 009）；append 路径上不偷偷删 |

## 二、为什么是归档后裁剪

I5 的售后要求是「崩溃后能解释数据从哪来」。只裁剪等于把这条链按长度截断：过了
阈值之后，**更早的状态变更就永远说不清了**，而这正是审计日志存在的理由。

归档让「删」变成一次搬家：库里留最近的、按需查，历史留在数据目录里、用户自己
的盘上，随时能翻。代价是多一个归档目录要管（见 §六）。

## 三、顺序是硬要求

```
读旧行  →  写归档文件（临时文件 → fsync → os.replace）  →  删行（一个事务）
```

| 崩在哪 | 结果 |
| --- | --- |
| 归档写到一半 | 目标文件不存在（原子换名没发生），旧行还在 —— 重跑即可 |
| 归档写完、删行前 | 归档在、旧行也在 —— 重跑会撞上「归档文件已存在」并报错，**不覆盖**，人工确认后再动 |
| 删行事务失败 | 本次刚写的归档被撤掉，旧行还在 —— 重跑即可 |

**方向只有一个：绝不先删。** 宁可多一份归档，也不许出现「日志里没有、归档里也没有」。

## 四、保留量怎么给

`keep` 是**条数**，不是天数：

- 时间口径要求先知道真实写入量，而现在还不知道 —— 先给计数口径，等日志量跑出来
  再把时间口径加进来；
- `keep=0` 合法：全部归档、库里清空（慎用）；
- `keep` 为负 = 用法错误，直接报错，不静默取绝对值。

宿主读到哪个 `keep`（以及它要不要在启动时轮转）由配置决定，键归组件声明（路线
001 的「声明 + 补齐」用法），不写死在核心里。

## 五、归档文件

| | |
| --- | --- |
| 位置 | `<数据目录>/event-log/`（与库、附件库同源，可整体搬走） |
| 名字 | `event-log-<首 seq>-<末 seq>.jsonl`，seq 补零到 12 位便于排序 |
| 内容 | 每行一个封套，**就是 `EventEnvelope.to_wire()` 的字节** |
| 已存在同名 | 报错，不覆盖 |

内容是封套自己的 wire 形式（不变量 I8）：归档不是另一种格式，它就是封套在文件里
的样子。所以归档能被 `EventEnvelope.from_wire()` 原样读回来，不需要第二套解析。

**不做压缩。** 现在没有量，压不压是伪问题；真要压，在写归档那一处加，格式不变。

## 六、明确不做

| 不做 | 为什么 |
| --- | --- |
| 在 append 路径上自动删数据 | 写一条日志顺手删掉别的日志，是 I5 最不该有的惊喜 |
| 按时间裁剪 | 见 §四：口径得从真实量里来 |
| 归档文件自身的轮转 / 清理 / 压缩 | 等真有量再说，现在做就是拍脑袋 |
| 归档参与数据库事务 | 文件系统不进 SQLite 事务（storage.md §六 同一条边界） |

## 七、验收

- 归档 + 留下的行 = 原来的全集，**不丢也不重**；
- 归档文件里每一行都能被 `EventEnvelope.from_wire()` 读回，并与原行逐字段一致；
- 归档写失败（或同名已存在）时，**一行都不许删**；
- 删行失败时，刚写的归档被撤掉，重跑能成功；
- `keep` 大于总数时不产生空归档文件，也不写盘；
- 轮转前后，`read_events()` 仍按 seq 升序返回剩下的部分。
