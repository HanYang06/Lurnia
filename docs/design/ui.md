# 界面：安静的工具

> 本文件是 Lurnia 界面的设计事实来源。**观感优先于命名**：颜色按眼睛选，
> 不按项目名的谐音选；配色是算出来的，不是挑出来的。

> **配图说明**：本文件的示意图（`assets/ui-*.png`）是**线框示意**，用于标注尺寸与色值，
> 不是真实界面截图。曾有一张 `lurnia-design-baseline.png` 作"一页总览"，
> 已删除：它把 `ui-*` 里的六张图拼了一遍（内容重复），且其中的标识是**已废弃**的旧形态。
> 演示图的渲染源与复现方式见 [`assets/render/README.md`](assets/render/README.md)。

## 一、审美主张

Lurnia 界面的性格是**安静**。不是冷淡，不是素净到没有表情，而是一个
**长时间开着不累、信息密度够高、不需要你侍候它**的工具。

由此推出五条不可协商的取向：

| 取向 | 含义 | 反面（本项目明确不要） |
| --- | --- | --- |
| **组合决定颜色，颜色不决定组合** | 先定动线与布局，颜色是随后施加的参数 | 因为某个颜色好看就改布局；先挑配色再拼结构 |
| **观感优先于命名** | 颜色因为好看、好读、好用而被选 | 因为"Lurnia 里有光"就把界面做成发光渐变 |
| **一个强调色** | 全界面一条色相轴，靠明度与彩度分层 | 彩虹式多强调色，每功能一色 |
| **安静优先于表达** | 装饰不得抢占内容；动效小、短、可关 | 大面积渐变、发光、拟物拟真、装饰性动画 |
| **颜色不单独承载语义** | 状态必须同时有形状、文字、颜色 | 只用红绿区分对错 |

**第一条是本文件其余部分的排序原则**：动线（§三）先于配色（§二）被真正解决，
配色不反过来要求布局让步。这也是为什么 §3.1 的四区栏位预算不因为"换个颜色更好看"
而改动。

第三条尤其重要：这是**知识工具**，屏幕上待最久的是正文。任何让正文让步的
设计都是本末倒置。

### 1.1 安静 ≠ 没有颜色

受众是**普通用户**（学生、非技术人群占多数），不是只服务技术工作者。
因此"安静"约束的是**工作界面**，不是整个产品：

| 层 | 是否受"安静"约束 | 说明 |
| --- | --- | --- |
| 工作界面（正文、列表、面板） | **是** | 色相归语义所有，装饰不得抢内容 |
| 品牌层（标识、启动页、安装包） | **否** | 可以有质感、可以多彩，见 §6.4 |
| 主题包（路线 098） | **否** | 用户可自行选艳丽配色，默认仍是安静的那套 |

**多强调色只在后两层被允许。** 工作界面里一个功能一个颜色，会把 I2 的三态
（§2.5）淹掉——那是本项目唯一必须守住的颜色语义。

## 二、调色板基线

![调色板基线](assets/ui-palette.png)

### 2.1 中性色：微冷青，不是灰

中性色不用纯灰。纯灰（`#888` 系）在屏幕上是**死的**——它不传递任何温度，
大面积使用会显得廉价、像未完成的线框图。

Lurnia 的中性色统一带 **色相 196、彩度 0.014** 的极轻冷青偏色。这个量的选取
是刻意的：

- **感觉得到**：与纯灰并排时能看出层次，界面显得"被设计过"；
- **说不出**：低到无法被命名为"绿色界面"或"蓝色界面"；
- **不变浑**：深色端不会像偏绿的中性色那样发脏、发霉。

代价与边界：彩度**不得超过 0.02**。超过之后，深色底会开始被读成"墨绿"，
而浅色底会开始偏黄绿——两个方向都坏。

### 2.2 强调色：青，且限在舒适带

强调色取 **色相 196**（青），全项目**仅此一条强调色轴**。

选 196 而非更蓝的 235 / 255，理由是观感而非偏好：

- **短波长的文字在深底上会光晕**。高饱和蓝紫作为正文/图标色时，人眼晶状体
  对短波长的折射更强，导致笔画边缘发虚、对比度被主观削弱。青（196）仍含有
  足够的绿色成分，落在"冷"这一侧却不进入光晕区间。
- **240 以上开始与深底的冷中性同化**，强调色不再"跳"，需要靠提高明度补偿，
  于是又滑向霓虹。

强调色明度被**限制在舒适带内**（深色 L 0.62–0.72，浅色 L 0.44–0.56）。
不设上限地追求最大彩度会把深色强调色推到 L≈0.9，视觉效果是**霓虹灯管**而不是
界面元素。彩度更高不等于身份感更强：当眼睛把它读成"信号灯"而不是"墨"的时候，
就过头了。

| 令牌 | 值 | 十六进制 |

浅色端**不反转**深色端的结构：底色不是纯白（`#fff` 在屏幕上刺眼、且让正文
对比过硬），而是 L 0.978 的极浅冷青；卡片比底色**更亮**（0.999），
于是"卡片浮在底色上"的层级关系在两个主题里方向一致，不需要用户重新学。

### 2.5 语义：三态同级（I2 的可视化）

这是本项目最特殊的一条。I2 规定 `Decision ∈ {ALLOW, DENY, UNCERTAIN}`，
三态**不得塌陷为 bool**。界面必须让这条不变量**看得见**：

![语义三态：I2 的可视化](assets/ui-states.png)

| 状态 | 深色 fill | 深色 ink | 浅色 fill | 浅色 ink | 形状 |
| --- | --- | --- | --- | --- | --- |
| `allow` | `#162b1c` | `#01db71` | `#dbf5e1` | `#007d3d` | `✓` |
| `deny` | `#361e1b` | `#ff4640` | `#ffe4df` | `#d30016` | `✗` |
| `uncertain` | `#2f230e` | `#f0a800` | `#fbead1` | `#8e6200` | `?` |

设计要点，逐条对应 I2 的意图：

1. **同级，不给特权**。三态使用**相同**的明度与彩度结构（fill 同为
   L 0.265 / 0.945，彩度同为 0.038），只有色相不同。任何一态若更亮、更饱和、
   更大，就等于在视觉上宣布它是默认值——I2 明确禁止"不确定时的默认值由调用点
   随手给"。
2. **低彩度填充，高彩度文字**。三态用**淡底 + 饱和字**，而不是整块高饱和色块。
   后者在深色界面上是刺眼的告示牌；前者既安静又清晰。
3. **颜色之外必须有形状与文字**。`✓` / `✗` / `?` 加状态名，与颜色**冗余**。
   色觉异常用户（deutan 约占男性 6%）与灰度打印下信息不丢。三态色相在
   deutan 模拟下会互相靠拢，因此**这条冗余不是可选项**。
4. **不确定性是一等状态，不是错误**。`UNCERTAIN` 用琥珀而非红，也不加警告
   三角图标——它是"需要人来裁"，不是"出事了"。

### 3.1 四区 + 脊柱 + 状态条

![布局：四区 + 脊柱 + 状态条](assets/ui-layout.png)

| 区 | 宽度 | 可折叠 | 职责 |
| --- | --- | --- | --- |
| 导航条 | 72px 固定 | 否 | 图标 + 文字标签，切换**模块**（笔记/项目/权限/AI）；底部固定"设置" |
| 列表栏 | 242px 固定 | 是 | 当前模块的条目集合；选中项以左侧 2.5px 强调条标识 |
| **日志脊柱** | 88px 固定 | 否 | **本设计的签名元素**，见 §3.2 |
| 读面 | 弹性，正文 `max-width: 58ch` | — | 正文；超过 58ch 不再拉宽，改留白 |
| 检视器 | 232px 固定 | 是 | 属性、标签、权限判定；默认展开 |
| 状态条 | 28px 固定 | 否 | 持久状态：本地/网络、版本数、不变量满足情况 |

**导航条用"图标 + 文字"而不是纯图标**。纯图标导航是桌面工具最常见的傲慢：
用户必须悬停才知道每个图标是什么。多花的 40px 宽度换掉整类猜测。

**正文限制在 58ch**。中文正文每行 30–40 字最舒适；`58ch` 在中文下约 29 字，
在等宽数字与英文混排下约为 58 字符。窗口拉宽时**留白增长，而不是行宽增长**。

**层级方向在两个主题里一致**：`bg → surface → surface-raised`，卡片始终比它所在的底
更亮。深色端用**明度**表达层级，而不是投影——深色底上的阴影几乎不可见。

### 3.2 签名元素：日志脊柱

![签名元素：日志脊柱](assets/ui-spine.png)

读面左侧一条 88px 的竖向脊柱，显示本文档的**版本时间线**（最新在上）。

为什么值得成为签名元素：

- 它把 **I5（先写事件日志，后落数据）** 变成**可见**的东西。用户不需要相信
  日志存在——它一直在屏幕左边。
- 它把 **I4（一切持久化数据带 version）** 从"技术约束"变成"日常界面"：
  版本是阅读体验的一部分，不是藏在菜单里的功能。
- 它回应本项目"个人知识平台"的本体：**你知道这份笔记从哪一版长成现在这样**。
  这是笔记工具很少给、而本项目的不变量恰好免费提供的视角。

交互：点击任一节点→只读查看该版本；`v3 现在` 节点高亮为强调色；
当前版本与历史版本用**实心/空心圆点**区分（形状冗余，不只靠颜色）。

### 3.3 响应式断点

![窗口收窄行为](assets/ui-responsive.png)

桌面 APP 的窗口是可缩放的，因此必须定义收窄行为。原则：
**先收检视器，再收列表栏，最后才动读面**——正文优先级最高。

| 窗口宽度 | 行为 |
| --- | --- |
| `≥ 1180px` | 完整四区 |
| `1000–1179px` | 检视器折叠为右侧图标条（悬停/点击展开为浮层） |
| `820–999px` | 列表栏折叠；导航条收为 48px 纯图标（此时才允许省文字），脊柱保留 |
| `< 820px` | 单栏：列表与读面互斥切换；脊柱转为读面顶部横向版本条 |

**脊柱在 `≥820px` 时不折叠**。它是签名元素，也是 I5 的可视证据；
在还能叫"桌面窗口"的宽度里，它不该被牺牲。

## 四、组件样式

![组件：深浅两套完整规格](assets/ui-components.png)

### 4.1 圆角、间距、层级

| 令牌 | 值 | 用于 |
| --- | --- | --- |
| `--lr-radius-sm` | 6px | 标签、徽标、小控件 |
| `--lr-radius-md` | 8px | 按钮、输入框、卡片内块 |
| `--lr-radius-lg` | 10px | 卡片、面板 |
| `--lr-radius-xl` | 13px | 应用主容器、模态 |
| `--lr-radius-app` | 22% | 应用图标（见 §6） |

间距基准 4px：`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40`。
组件内部用 4 的倍数，**不允许** 5px、7px、13px 这类随手值。

### 4.2 状态

每个可交互元素必须定义**六个**状态，缺一不可：

| 状态 | 表达方式 |
| --- | --- |
| default | 基准 |
| hover | 深色端明度 +0.04；浅色端明度 −0.03 |
| active/press | 沿**远离自身文字颜色**的方向移动（见下） |
| focus | **2px 强调色环 + 2px 偏移**，不用 `outline: none` |
| disabled | 整体不透明度 0.45，且 `cursor: not-allowed`，不改变颜色 |
| selected | 左侧 2.5px 强调条 + `--lr-surface-raised` 底 |

**按压方向的规则**（容易被忽略的细节）：填充色的按压/悬停方向由**该填充上的
文字颜色**决定，而不是由主题决定。

- 深色端：填充上是**深色字** → 按压时填充**变亮**；
- 浅色端：填充上是**浅色字** → 按压时填充**变暗**。

直觉上会写成"深色主题里按压变暗"，但那样会让深色按钮上的深色文字对比度
从 4.7:1 掉到 3.6:1 —— 打字时文字糊掉。方向必须跟着字走。

### 4.3 焦点可见性

焦点环是可用性基础设施，不是装饰：

- 键盘焦点：`2px --lr-accent` 外环 + `2px` 偏移，圆角跟随元素；
- **不得**以 `outline: none` 移除后不补替代物；
- 焦点环在深浅两端均须与底、与元素本身可区分（§101 已按此验证）。

### 4.4 动效

短、小、可关。

| 令牌 | 值 | 用于 |
| --- | --- | --- |
| `--lr-dur-fast` | 120ms | 悬停、按压、开关 |
| `--lr-dur-base` | 180ms | 展开、折叠、面板滑入 |
| `--lr-ease` | `cubic-bezier(.2, 0, 0, 1)` | 标准缓出 |

必须响应 `prefers-reduced-motion: reduce`：时长归零，仅保留状态变化，
不做位移与缩放。**动效不得成为信息本身**——任何"必须等动画看完才知道结果"
的交互都是缺陷。

## 五、主题切换与深浅色

- **跟随系统为默认**，但允许手动锁定深/浅/跟随三态。
- 切换是**瞬时**的：不做"渐变过渡"（全屏插值会让人短暂失去方向感）。
- **两个主题都是完整规格**，浅色不是深色的附属品：§2.3 与 §2.4 各自独立
  验证过对比度，不靠"深色能过所以浅色应该也行"。
- 主题令牌以 `:root` + `[data-theme="dark"|"light"]` 提供，
  语义令牌名两主题**完全一致**，只有值不同——组件代码不得出现
  `if (darkMode)` 这类分支。

## 六、标识（logo）

![标识：六片叶片环绕核心](assets/review-09-logo-iris.png)

### 6.1 形态

**六片等角叶片，环绕一个分离的核心**。叶片在圆周上等距分布、**彼此不粘连**；
核心与外圈之间**留有空隙**。

几何参数（`viewBox 0 0 128 128`）：

| 参数 | 主标识 | 小尺寸变体 | 作用 |
| --- | --- | --- | --- |
| 叶片数 | 6 | 6 | |
| 外径 / 内径 | `58` / `30` | `58` / `30` | 内径决定核心与外圈之间的空隙 |
| 缝隙角 | `5.5°` | `11°` | 小尺寸加倍，见 §6.3 |
| 核心盘半径 | `23` | — | **圆的半径**（开口），比叶片暗 |
| 核心内藏 | 平面蜂窝投影到球面：孔径 `23` / 球半径 `51` / 格径 `9`，缝 = 格径 `10%` | — | 见下 |

**核心必须是低调的**——这是硬约束，不是风格偏好：

1. **不得有高光**。中心不是光源，是"内核"；画成亮点就把最该收敛的元素变成最抢眼的元素。
   语料里也正好相反：内核是**被围着**的那个，不是发光的那个。
2. 核心是**凹面**：比叶片更暗，受光侧（左上）内侧一道阴影，形成内凹而非外凸。
3. 核心是一个**圆**——轮廓是**完美的圆**，球面立体感只在内部。
   **它不是球**：看到整条轮廓（表面一直弯到消失）才会读成"小球／高尔夫球"，
   所以这里用开口切出一个圆，并且**不做边缘变暗**。
   放大后的独立文件是 [`assets/lurnia-core-disc.svg`](assets/lurnia-core-disc.svg)。

   | 参数 | 值 | 理由 |
   | --- | --- | --- |
   | 孔径 A | `23` | **圆的半径** |
   | 球半径 S | `51` | **S/A = 2.2**，边缘倾角 `27°` |
   | 格径 | `9` | viewBox 单位（48px 下仍可辨） |
   | 可见格数 | `19` | 由开口裁切 |
   | 明度区间 | `0.045 – 0.275` | **在圆内归一化**；线性光，输出时转 sRGB |

   **做法**（与独立圆盘共用同一套）：一副**平面规则六边形网格**，摊在**弧长空间**
   （球面摊平，格子在那里是精确的正六边形）；格点按 `θ = s/S`、`r = S·sin θ`
   **只投影一次**，每格取自己那六个**已投影**顶点连成多边形；明度取该格法线
   （`nz = √(1 − (ρ/S)²)`）与单一光源方向的点积，并在孔径内归一化。

   > **格点必须只投影一次。** 早期是把每个六边形**绕自身中心**旋转 + 径向压缩后再摆到
   > 格点上——于是同一个格点被算了两遍、落在两个位置（实测相差 `9.6`，约 18.5% 棱长），
   > 棱与棱既不平行也不等距，缝宽在 `0.14–11.48` 之间乱跳。顶点投影让"边对边、角对角"
   > 成为构造上的恒等式：缝 = 0 时实测 **438 条内部棱全部恰好被 2 格共用、438 个内部
   > 顶点全部恰好 3 格相交，越界 `0`**；带 10% 缝时缝宽恒为 `√3 × 格径 × 10%`，只在
   > 边缘按 `cos θ` 收缩（cell 36：圆心 `6.22` → 边缘 `5.68`）。见
   > [`assets/review-18-core-disc.png`](assets/review-18-core-disc.png)（对齐 / 密度 / 缝 /
   > 弧度四组实测，含旧版对照）。

   **为什么用平面网格、而不是按球面极角分环**：极坐标分环会让**格子本身畸变**，
   读起来是"不规则多边形"而不是蜂窝（早期试过；那一版的渲染源已随重做被替换）。
   平面网格的格子在与球面对应的**弧长空间**里始终是**规整六边形**，画到屏幕上只按
   `cos θ` 径向收缩，曲率全部交给明暗与这层收缩表达。

   **三条硬约束**（都踩过坑）：

   - **球必须大**。S/A = 1.0 时看得见整条轮廓，就读成一颗小球；S/A 太大又太平、
     读不出弧度。`2.2` 是中间那个位置。
   - **不得有边缘变暗**。可见边是**开口**切出来的，不是球的轮廓——加轮廓变暗
     等于宣布"这是一颗小球"。
   - **明暗必须在圆内归一化**。否则球一大、明暗梯度就消失。这是把"曲率可读性"
     与"球的大小"解耦的关键。

   **与叶片必须留出净间隙**：孔径 `23` + 内侧阴影描边 `2.6` ⇒ 与叶片内径 `30`
   之间有 **`5.7`** 的净间隙（24px 下仍有 1.1px）。间隙过小时内核在顶部会与叶片
   粘连成一块，这是实测出来的（曾只有 `0.7`）。

**为什么是「填充 + 深缝」而不是镂空**（四种取法都实测过，见
[`assets/review-14-core-variants.png`](assets/review-14-core-variants.png)）：

| 取法 | 结论 |
| --- | --- |
| **填充 + 深缝（缝 = 格径 10%）** | ✅ **选它**。同时保住"球面 + 蜂窝结构 + 哑光低调" |
| 镂空（只画线） | ❌ 64px 以下糊成噪点；且线一多必然发亮，与"内核低调"冲突 |
| 填充 + 无缝 | ❌ 丢掉蜂窝，读成一颗普通低多边形球 |
| 格径再缩小（46 格） | ❌ 结构变细，缩小后同样趋近噪点 |

**这个球面可以真滚动**——因为格子是**按角度参数化生成**的，不是烘焙好的图片。
绕竖直轴旋转、背面格子按 `z` 剔除即可；实测 0–75°（每帧 15°）可见格数在
25–29 之间变化、形态稳定，见
[`assets/review-15-core-rolling.png`](assets/review-15-core-rolling.png)。
这是选它、而不是选一张静态图的主要原因之一。

> **已废弃的早期方案**：三段等长弧 + 圆心。两处硬伤：① 与 **Blender** 的标识
> 近乎同构（Blender 同属工具类、同一受众圈层）；② 三段弧在 16px 下间隙只剩约
> 2px。全过程见 [proposals/logo.md](proposals/logo.md)。

### 6.2 为什么是这个形状

标识承载的是一个**结构隐喻**，不是一份工程说明：

| 元素 | 含义 |
| --- | --- |
| **中心的内核** | **内核**。所有东西围着它转，但它是被单独画出来的一块；**它是低调的**，不发光、不抢镜。 |
| **核心里内藏的蜂窝结构** | 内核里**装着有规则的东西**——结构清晰、可以滚动，但对外保持安静。这是"内敛"在图形上的落点：**凑近才有，不看也在**。 |
| **外围六片叶片** | **各个模块**。各自独立、互不粘连，绕同一个中心分布。 |
| **核心与叶片之间的空隙** | 模块彼此相邻，但**没有长在一起**。 |
| **旋转对称、无起点、无箭头** | 工具不规定工作流（"no forced workflows"）。 |

一句话：**一个内核，四周是各自独立、围绕它协作的模块**——这正是 Lurnia 的架构本身。

> **别把这张表当成"用户会读懂"的理由。** 品牌研究的一致结论是标识的首要功能是
> **识别**，含义靠长期使用习得，不是从图形解码出来的。上表是**设计溯源**，
> 用于日后判断"这个改动是否偏离了初衷"，不是传达承诺。

### 6.3 变体与使用约束

| 场景 | 文件 | 说明 |
| --- | --- | --- |
| 主标识（深色底） | `assets/lurnia-mark.svg` | 字面色 `#00babc`，任意尺寸 |
| 主标识（浅色底） | `assets/lurnia-mark-light.svg` | 字面色 `#007a7b` |
| 内联变体 | `assets/lurnia-mark-inline.svg` | `currentColor`，**内联进 APP 用**，跟随主题 |
| 小尺寸专用 | `assets/lurnia-mark-small.svg` | 缝隙 `5.5°→11°`，**中心留空**，供 16px |
| **核心圆盘（外部用）** | `assets/lurnia-core-disc.svg` | 内核单独导出（512×512，透明底）。**它不是球，是一个圆**：轮廓是完美的圆，球面感只在内部 |
| **基础版（灰度母版）** | `assets/lurnia-mark-base.svg` | **彩度恒为 0**。所有着色版都由它派生，见 §6.4 |
| 六叶轮（品牌层） | `assets/lurnia-mark-spectrum.svg` | 每片叶子一个色相，明度与基础版一致 |
| 应用图标 | `assets/lurnia-appicon.svg` | **透明底、满画布**（由系统施加圆角遮罩），含质感 |
| 横排组合 | `assets/lurnia-lockup.svg` | 标识 + 字标，用于关于页与文档头 |

**核心圆盘（外部用）**与标识内核同一套取法、同一套比例，只是把孔径放大到 `232`、球放大到
`516`（S/A 仍是 `2.22`，边缘倾角 `27°`）：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 孔径 / 球 | `232` / `516` | 512 viewBox 单位；圆外透明 |
| 格径（弧长空间） | `36` | 旧版是 `52`，密度不够 |
| 可见格数 | `73` | 旧版 `37`；`--cell 44 → 55`、`30 → 91`、`24 → 151` |
| 缝 | `10%` | 在弧长空间取，随格子一起按 `cos θ` 收缩 |
| 明度区间 | `0.045 – 0.275` | 线性光，在孔径内归一化，输出转 sRGB |
| 光源 | `(-0.5, -0.6, 0.63)` | 屏幕坐标归一化；左上、略朝观察者 |

它由 [`script/gen_core_disc.py`](../../script/gen_core_disc.py) 生成——**改参数就重跑，
不要手工改那 73 个多边形**：

```bash
uv run python script/gen_core_disc.py                    # 按默认值重写资产
uv run python script/gen_core_disc.py --cell 44 --seam 0 --sphere 417.6
```

生成器在落盘前会先把结果交给 XML 解析器：`<img>` 引入的独立 SVG 是**严格 XML**，
注释里出现 `--` 就是整张裂图，而同一份文件内联进 HTML 却不会报错——这个坑踩过一次，
所以现在解析失败即构建失败。

**关于颜色继承的实测结论**（两个坑都已验证，别再踩）：

- `<img src="...svg">` 加载的独立 SVG **没有级联可继承**。因此独立文件里的
  `currentColor` 会**解析成黑色**——不是主题色。
- 更隐蔽的是：独立文件里写 `var(--lr-accent, #00babc)` 会让 Chromium
  判定为**图片损坏**，直接显示裂图。`var()` 的 fallback 在这里不救场。
- 所以：**独立文件用字面色**；需要跟随主题时用 `-inline` 变体**内联**进
  HTML，而不是用 `<img>` 引用它。

约束：

- **最小尺寸 16px**，用 `lurnia-mark-small.svg`。该变体的两个参数都是**实测**结果，
  **不要按直觉改**：
  - **缝隙 5.5° → 11°**。主标识的缝隙在 16px 下只剩约 1.5px，六片会糊成一圈；
    加倍后核心与外圈之间的空隙才留得住。
  - **中心留空，不放亮点**。16px 下核心的凹面与蜂窝球面都不可辨；这时候画一个亮圆点
    会变成整个标识最响的一处，正好与 §6.2"内核低调"相反。留空即正确：
    暗心 + 亮环，读起来仍是"围着一个内核"。
  - **不要靠"加大外径"来救小尺寸**：外径吃满画布会挤掉下面的留白约束。
- **留白**：标识四周至少 `0.25 × 标识尺寸` 不得有内容。
- **单色优先**。`lurnia-mark*.svg` 只允许用 `--lr-accent`、`--lr-text-strong`、
  纯黑、纯白四种颜色；**不得**加渐变、发光、投影、描边外发光。
- **唯一的例外是对外资产**（应用图标、品牌层）：它们需要在大尺寸下被识别为
  "有体量的东西"，因此允许单一光源方向 + 逐叶片高光边 + 核心柔和辉光。
  即便如此，**仍不得**使用投影或外发光——那是 2010 年代的手法。
- 浅色底用 `#007a7b`（浅色版强调色），深色底用 `#00babc`；
  两者已分别验证对比度（§7.2）。

### 6.4 基础版与着色（对外 / 对内）

标识分两层，**几何形状只有一份，颜色按层授权**：

| 层 | 用在哪 | 颜色 |
| --- | --- | --- |
| **对内**（工作界面） | 导航栏、关于页、标题栏 | **单色**，只允许 `--lr-accent` / `--lr-text-strong` / 纯黑 / 纯白 |
| **对外**（品牌层） | 应用图标、启动页、安装包、宣传物 | **不限**，可以是六叶轮或任意配色 |
| **核心（所有层一致）** | 标识的中心 | **恒为中性**（彩度 0）。内核不参与配色，见 §6.1 |

核心在**任何**变体里都是中性色：换配色时只有叶片变色。这样"内核"在所有场景下
都是同一个东西，六叶轮也不会把中心染成第七种颜色。

对内的单色不是保守，是**纪律**：工作界面里色相已经归语义所有（§2.5 三态、I2），
标识再带色就会和状态色抢读者。

**着色模型（"先做灰度、再着色"的机械化版本）**：

```
基础版 = 只定义明度的母版          →  lurnia-mark-base.svg（彩度 0）
着色版 = 基础版 + (色相 H, 彩度 C)  →  明度不变，只换 C/H
```

实现上有一条**必须遵守的细则**：sRGB 是伽马编码的，**逐通道插值会让中间点的明度漂移**。
实测（叶片渐变 0.52 → 0.13）：

| 渐变色标数 | 明度漂移上限 |
| --- | --- |
| 2（默认线性渐变） | `0.038` |
| 5 | `0.004` |
| 9 | `0.0011` |
| **17** | **`0.0003`** |

所以**每个渐变至少要 17 个色标，且每个色标都按目标明度反解**——不能只写首尾两色。

渲染级验证（把三个版本画进 canvas、线性化后逐像素比亮度，256×256）：

| 对比 | 全部像素最大差 | **仅实心区（α=255）** | 低透明度边缘 |
| --- | --- | --- | --- |
| 单色青 vs 基础版 | 78.7% | **1.43%**（平均 0.24%） | 2638 px |
| 六叶轮 vs 基础版 | 25.3% | **2.93%**（平均 0.23%） | 2638 px |

那个 78% 全部来自轮廓上的低透明度像素——**预乘 alpha 在低不透明度下的量化误差**，
与颜色无关。实心区残差 ≤3%，出现在笔画叠加的交界处，肉眼不可辨。

结论：**换配色不需要重画标识**，改 `(H, C)` 即可，且永远不会破坏灰度下的可读性。
验证图见 [`assets/review-11-mark-base-proof.png`](assets/review-11-mark-base-proof.png)。

### 6.5 标识动画

标识是**唯一**允许有自己动效的元素——它出现的位置（启动、关于页）不承载信息，
动一下不打断任何人。分解图见
[`assets/review-10-logo-animation.png`](assets/review-10-logo-animation.png)。

| 场景 | 时长 | 缓动 |
| --- | --- | --- |
| 启动（一次性，结束即静止） | 400–600ms | 缓出 |
| 悬停 | 150–250ms | 标准 |
| 空闲呼吸（**默认关闭**） | 周期 **≥ 8s** | 缓入缓出 |

- 缓动曲线用 §4.4 的 `--lr-ease`（`cubic-bezier(.2, 0, 0, 1)`），**不新增曲线**。
- 只动 `transform` / `opacity` / `filter`——GPU 合成，不触发布局重排。
  本地 APP 完全吃得下这个开销。
- 幅度：旋转 ±5.5°、缩放 ±2.2%。**旋转与缩放不要同时用**。

**四条廉价感触发条件，占一条就翻车**：

1. 启动动画**遮挡内容超过 1s**；
2. **无限高频脉冲**（周期小于 8s 的常驻循环）；
3. 旋转与缩放**同时**上；
4. **没有 `prefers-reduced-motion` 分支**。

第 4 条是硬性要求：`prefers-reduced-motion: reduce` 下**时长归零、直接显示终态**
（WCAG 2.3.3）。这与 §4.4"动效不得成为信息本身"是同一条原则——动效只允许出现在
**启动、切换模块、保存成功**这类一次性事件上，**不得做成常驻大动画**。

## 七、对比度与无障碍

### 7.1 目标（已全部实算验证）

| 内容 | 目标 | 依据 |
| --- | --- | --- |
| 正文、标题、次要说明 | ≥ 4.5:1 | WCAG 2.1 AA |
| 三态 ink 对其自身 fill | ≥ 4.5:1 | 同上 |
| 控件边界（`border-strong`）、非文本指示 | ≥ 3:1 | WCAG 1.4.11 |
| `text-faint`（大字/非正文） | ≥ 3:1 | WCAG AA 大字 |
| `border`（纯装饰分隔线） | ≥ 1.2:1 | 可感知即可，不承载信息 |
| 焦点环 | ≥ 3:1 对底与对元素 | WCAG 1.4.11 |

验证方式：把每个前景色对**该主题下全部三个层级底**（`bg` / `surface` /
`surface-raised`）分别计算对比度，取**最差**结果判定。只对页面底色验证是
不够的——真实内容坐在卡片上，卡片坐在页面上。

### 7.2 已验证结果（深色 / 浅色）

| 检查 | 深色 | 浅色 |
| --- | --- | --- |
| 正文 on bg / surface / raised | 13.35 / 12.48 / 11.23 | 12.30 / 11.47 / 12.80 |
| `text-muted` 最差 | 6.49 | 5.99 |
| `text-faint` 最差 | 4.10 | 4.08 |
| `border-strong` 最差 | 3.05 | 3.02 |
| `accent` 最差 | 6.70 | 4.54 |
| `on-accent` on `accent` | 7.14 | 5.04 |
| 三态 ink on fill（最差） | 4.57 | 4.54 |

表中数值为**对三个层级底取最差**后的结果，由脚本实算得出，非估算。

### 7.3 不依赖颜色的规则

以下规则是硬性的，不得以"颜色已经够了"为由省略：

1. **状态必须冗余编码**：色 + 形状 + 文字，三者至少存在两者。
2. **不得用红/绿作为唯一区分**，尤其在权限判定与 diff 中。
3. **图表不得只靠色相区分系列**，须加形状或直接标注。
4. **灰度打印可用**：语义信息在去色后仍完整（三态的 `✓/✗/?` 即为此设计）。
5. **最小点击目标 24×24px**（桌面指针场景按 WCAG 2.2 最低要求）。
6. **文字放大到 200% 不丢失功能**，不出现横向滚动。

### 7.4 已记录的风险

- 三态色相在 **deutan / protan 模拟下互相靠拢**，`allow` 与 `uncertain`
  会变得接近。这是采用红/绿/琥珀语义的固有代价，**无法用调色解决**，
  因此以形状与文字冗余作为对策（§7.3 第 1 条）。
- `text-faint` 在深色最浅底上为 4.10:1，**仅可用于大字或非正文元素**。
  若将来要把它用于正文，必须重新求解明度。

## 八、组件库与状态

<a id="r104"></a>

- 组件库**先从"原语"开始**，不从页面开始：`Button`、`Input`、
  `Select`、`Checkbox`、`Switch`、`Tag`、`Card`、`Table`、`Toast`、
  `Dialog`、`Meter`、`Skeleton`、`StateBadge`（三态徽标，特例，见 §2.5）。
- **所有颜色只能通过语义令牌引用**，组件内不得出现十六进制字面量。
  这是保证 §5"两个主题完整对等"的唯一机械手段。
- `StateBadge` 是**唯一**允许内置三态语义的组件；其他组件不得自行猜测
  状态颜色——三态的判定与呈现都归 I2 的唯一定义。
- 状态管理不进入本设计文档的范围（见路线 104 的独立设计）。

<a id="r105"></a>

## 九、与内核的边界

**界面不得反向定义内核。** I7 规定内核不知道 UI 存在，因此：

- 界面消费的是内核**已有的**事件封套与 `Decision` 三态（I8），
  不为界面便利新增内核字段；
- 三态在界面上**不得**被折叠成布尔——`StateBadge` 接收的就是三值枚举，
  不得出现 `if (allow)`；
- 界面的"谁在操作"来自 `Subject`（I6），不自行造身份概念；
- 一切对外动作（开链接、导出、联网）必须由用户显式发起（I9）。
  界面**不得**在渲染过程中触发任何对外行为。

## 十、待裁事项

以下问题**尚未决定**，不要在实现时默认选择：

1. **正文是否提供衬线阅读字体**。衬线在长文阅读上可能更舒适，但中文衬线
   字体在 Windows/WebView 上的一致性差，可能反而伤害观感。需要实机试读后定。

   只用强调色 + 中性色，分类靠图标与文字；但若标签系统需要视觉区分，
   需要新增一条**受控**的辅助色轴，并按 §7.1 重新验证。
