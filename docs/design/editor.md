## 一、裁定摘要

| # | 裁定 | 代价 |
| --- | --- | --- |
| A1 | 正文的存储格式是 **JSON 文档树**，不是 Markdown、不是 HTML | 需要导入/导出桥；换来锚点、节点级 diff、文字级权限可行 |
| A2 | **权威**（校验、迁移、落盘、索引）在组件层 Python；前端只做编辑行为与渲染 | 提交需跨界一次；换来模型被 mypy strict / coverage 90% 覆盖 |
| A3 | 两侧**只有一个 schema 来源**（声明式资源，在 Python 包内），前端在构建期由它生成编辑器 schema | 多一个生成步骤 |
| A4 | 块级节点带稳定 id（`uuid.uuid7()`，标准库，时间有序）；行内节点不强制 | 块 id 的体积 |
| A5 | 撤销/重做是**会话内**的 step 栈，不落库；修订只在**提交点**产生 | 撤销不跨会话 |
| A6 | 「引用」拆成两个不相干的东西：**引用块**（内容）与**笔记引用**（指向另一篇） | 两个节点类型 |
| A7 | 「标注」拆成两个不相干的东西：**批注**（文档外实体、可孤儿）与**高亮**（文档内标记） | 两套生命周期 |
| A8 | 不开放 **typeface / 字号 / 颜色**选择；只有语义样式与主题令牌 | 用户不能把笔记做成海报 |
| A9 | **渲染期零网络**：远程图片/字体/样式一律不加载；粘贴进来的远程资源必须本地化成附件，否则显式占位 | 粘贴多一步失败提示 |
| A10 | 前端编辑器用 **ProseMirror**，schema 由 A3 的单一来源生成 | 引入一个前端依赖 |
| A11 | 宿主 → 内核的请求需要 stdio **`call` / `reply` 帧（协议 v2）**，sidecar 开始解析 stdin | 边界协议升级，三处同时改 |
| A12 | **业务 schema 归组件包**（`components/<名>/sql/<schema>/`），内核只装内核自己的表 | 加载器要补「schema → 包」解析（storage.md §五） |
| A13 | 写入分两档：**自动落盘不产生修订**，修订只在显式提交时产生 | 多一个档位概念；换来库体积与日志脊柱都干净 |
| A14 | 表格：行列 + 表头，**不做合并单元格、不做嵌套** | 复杂表格要等锚点、粘贴、导出三处一起升级 |
| A15 | **存储只认「文档 + 文档类型」**（`doc.doc_type`），不认「笔记」 | 多一层间接；换来加一种编辑器不改库 |
| A16 | 校验器**按 schema 编译成单遍计划**，禁用通用 JSON Schema 引擎 | 要自己写校验器；换来常数小一个量级 |
| A17 | **FTS 更新与自动落盘解耦**（实测它占保存开销的 80%） | 检索最终一致，落后最多一个提交点 |
| A18 | 通用性**在契约与形态上拉满，在结构上克制**：管道只有一套、形态只有四种、字段清单等需求 | 现在不产出其它编辑器的结构；换来不被未验证的契约绑住（§3.4） |

一句话：**用户看到的是 Word 那样的直接编辑；底下是带稳定身份的结构化文档；Markdown 只是进出口。**

## 三、分层与权威归属

**正文的权威在组件层（Python），编辑行为在前端。** 三个理由，按硬度排序：

1. **路线图把编辑器放在组件层**（`## 路线增量` → 组件层 → 笔记模块 → 编辑器）。
   层级是归属，不是实现细节。
2. **仓库的质量门只覆盖 Python**：`uv run python -m mypy .`（strict）、
   `pytest --cov`（`fail_under = 90`）。前端没有测试门禁。把模型放在没人守的一侧，
   等于把「测试承载重量」这条项目铁律作废。
3. **依赖正文的下游能力都在 Python 侧**：文字级权限（018）、版本与 diff
   （024 / 025）、反链索引（111）、全文检索（FTS5，storage.md §三）。

**「权威」指裁决权，不是「每次按键都过 Python」。** 前端持**工作副本**（编辑手感必须
本地完成，逐键跨进程往返不可接受），提交时才跨界校验与落盘（§六）。校验在 Python 是
**第二道**：前端清洗是体验，Python 校验是裁决（§十五）。

**两侧只有一个 schema 来源**（A3）：schema 是**数据**，放在
`src/lurnia/components/note/schema/note.schema.json`，随包分发（packaging 冻结只收包内
的东西，storage.md §五 同一条教训）。Python 在运行期用它校验与迁移；前端在**构建期**
由它生成编辑器 schema。禁止两侧各手写一份节点清单 —— 那就是两份事实，必然漂移。

### 3.1 一条管道，多种编辑器

**「编辑器」不是指文本编辑器，是指一套体系。** 今天只有文本（`note`），将来还会有画布
（035/036）、设计器（051–061）之类。它们**共用同一条管道**：

| 管道段 | 谁提供 | 对每种编辑器是否相同 |
| --- | --- | --- |
| 文档读写、事务、修订、提交点 | 文档存储（114） | **相同** |
| 批注、高亮锚点、引用与反链 | 文档模型与类型注册（108） | **相同**（锚点是通用坐标，§五） |
| 全文检索（FTS5）、悬空引用判定 | 文档存储（114） | **相同** |
| 宿主、工具栏框架、插入入口、检视器、查找替换**界面** | 编辑器宿主（117） | **相同** |
| 节点类型、schema、迁移链、纯文本与引用的抽取规则 | **每种编辑器自己交** | **不同** |

**所以「加一种编辑器」= 注册一个文档类型**，不是新写一套存储、也不是给数据库加表
（A15）。这是本文对「可扩展」的全部承诺，也是它唯一不敢省的地方：
契约在这里，实现可以晚来。

### 3.2 每种编辑器必须交的东西（扩展点契约）

<a id="r117"></a>

一个文档类型（doc type）注册时**只交四样**，其余一律复用管道：

| # | 交什么 | 用途 |
| --- | --- | --- |
| 1 | **节点 schema**（声明式资源） | 校验、前端生成编辑器 schema |
| 2 | **迁移链**（纯函数 `migrate_N_to_M`） | I4：老文档打不开就是这里没做 |
| 3 | **抽取器**：文档 → 纯文本（给 FTS）、文档 → 引用集（给反链） | 检索与引用是全类型共享能力 |
| 4 | **能力声明**：是否支持表格 / 批注 / 高亮 / 引用（§4.2 清单的一个子集） | 宿主据此决定工具栏显示什么，**不写 `if (docType)`** |

**第 4 条是纪律**：宿主不得对文档类型做 `switch`。哪一项能力可用，来自类型自己的声明；
和 ui.md §八「组件内不得出现十六进制字面量」是同一种机械保证 —— 一旦有分支，
「一套体系」就退化成「几个特例」。

**明确不做**：编辑器插件不得自行落盘、不得自行开事务、不得绕过总线调用（I1 / I5）。
它只交文档数据，落盘归文档存储。

### 3.3 性能预算：Python 在哪、不在哪

先把边界说死：**按键、光标、选区、IME 组合、撤销栈、语法高亮、画布交互都在前端**，
Python 一个字节都不看。跨界的只有四件事：打开文档、保存、检索、查批注/反链。

实测（本机 Python 3.14.8 / SQLite 3.53.1，**2.07 MB** 文档：2500 个块、75 万字纯文本，
已明显大于真实笔记）：

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| `json.loads` | 3.7 ms | 标准库 C 实现 |
| 单遍校验 | 1.1 ms | 手写的简化走查；完整校验按 2–4 倍估 |
| `json.dumps` | 6.7 ms | **保存路径应当避免它**（见下） |
| SQLite 写 doc 一行 | ~2 ms | WAL |
| **FTS5 全行重写** | **40.1 ms** | **占八成，且随文本量线性增长** |
| FTS 查询 | 0.08 ms | 库再大也基本是这个量级 |

由此定死五条口径：

1. **不用通用 JSON Schema 引擎**（A16）：那是纯 Python 逐节点解释，常数大一个量级。
   校验器按 schema **编译成单遍计划**，启动时编一次。
2. **保存不做 re-dump**：前端发来的 JSON 文本，校验通过后**原样入库**。
   既省掉 6.7 ms，也避免"存进去的和校验过的不是同一份"。
3. **FTS 挪到提交点**（A17）：自动落盘只写 doc 行 + 事件日志；
   FTS 在显式提交时更新。检索因此**最终一致**，落后最多一个提交点 ——
   它是派生数据（storage.md §八），落后可接受，阻塞编辑不可接受。
4. **反链只在本篇引用集变化时更新**：抽取 + diff 引用集，成本与引用数同阶，不是全文量级。
5. **上限与降级**：单文档硬上限（暂定 8 MiB，见 §二十二）超了返回 `Err(INVALID)` 并明示；
   接近阈值（1 MiB）只告警。

**于是"Python 吃得消吗"的答案是：吃得消，而且余量很大。** 自动落盘路径 ≈ 6 ms（2 MB 文档，
不含 FTS），频率是 3 秒一次；真实笔记 20 KB 量级时在毫秒以下。**真正会压垮 Python 的只有
一种做法：让每次按键或每次操作都过边界** —— 协作若走"每操作一次 IPC"就必须重新设计
（前端持 CRDT、Python 只做周期快照），这条不阻塞今天。

**留一句退路在明处**（同 §二十一.2）：若将来校验也必须下移到前端，边界可以整体前移，
代价是模型脱离 Python 的质量门禁。

### 3.4 通用到什么程度：契约与形态拉满，结构留给需求

**先亮一条容易被忽略的账：维护成本跟「管道数量」成正比，跟「类型数量」几乎无关。**
类型只是注册项（§3.2）；真正会把人拖死的是**多套存储、多套锚点、多套检索**。
所以"奔着通用走"的正确落点不是把所有结构合并成一个万能结构，而是：

| 层 | 策略 |
| --- | --- |
| 管道（存储 / 修订 / 提交点 / 锚点 / 引用 / 批注 / 检索） | **只有一套，永不复制** |
| 形态（树 / 网格 / 图 / 二进制） | **现在就定**，见下 |
| 具体结构（字段清单） | **需求来了再定**，见下 |

**四种文档形态（现在的通用化落点）。** 任何新编辑器进来，第一件事是**认领一种形态**，
而不是发明一套结构：

| 形态 | 通用承载 | 今天的实例 |
| --- | --- | --- |
| **树**（嵌套 / 线性块） | `content` 树 + 块 id + 行内标记 | 文本（`note`，§四） |
| **网格**（行列） | `table` / `table_row` / `table_cell`（§4.7） | 表格（116） |
| **图**（节点 + 边） | 节点集合 + 边集合 + 节点坐标；**锚点挂在节点 id 上** | 画布、逻辑图、架构图（035/036、057–059，全未定） |
| **二进制 / 附件型** | 本体进附件库（107），文档里只留薄描述 JSON | 图片 / 视频 / 音频的编辑态（040–042） |

**本文只定这四种形态的承载方式与坐标，不定任何一种的字段清单。** 图的锚点到底挂节点
还是也挂边、设计器的"图层"是不是一种节点，这些等需求进来再定——现在定就是猜（§二十一.6）。
形态本身是可扩展的分类，不是 schema：真有需求不属于这四种，就加第五种，成本很低。

**类型准入（防增殖的机械约束）。** 注册一个文档类型，除了交 §3.2 的四样，还要书面回答
一句「**为什么不能复用已有类型？**」，并满足三条硬约束：

1. **不得自带存储、不得自带表** —— 存储只有一套（§十七）；
2. **不得自带锚点、引用、批注、检索** —— 这四样是全类型共享能力，只有一种实现；
3. **缺口先补能力、后建类型** —— 能靠能力声明（§3.2 第 4 条）表达的需求，不许新建类型。

**为什么"顺手把其它编辑器的结构都定掉"是反的。** 结构对不对，只能由需求验。
现在把 20 多个未定条目（035/036、045–092……）的结构写进设计，产出的是**20 多份
看起来权威、实际没被任何需求验证过**的契约；第一个真实需求落地时它们会被推翻，
而"推翻已经写进事实来源的东西"比新增一个类型贵得多。

**所以"100 个需求 = 100 个结构"的真正解药不是提前猜，而是上面那三条约束**：
一个需求一个**类型**可以接受（类型是注册项，加一个不影响别人）；一个需求一套
**存储 / 锚点 / 检索**才是灾难 —— 那才是谁都维护不下来的那种局面。
本文把管道锁成一套，就是为了让前一种情况永远不变成后一种。

## 四、文档模型（r108）

<a id="r108"></a>

> **通用契约 vs 具体类型**：§4.1–4.5 是**通用契约**——任何文档类型都适用，含将来的画布
> 与设计器；§4.2 的节点清单、§4.6、§4.7 是**文本类型 `note`** 的具体形状。
> 两者不要混：前者改了要动所有编辑器，后者改了只动文本编辑器。

### 4.1 树形状

```
doc    = { "doc_type": <str>, "version": <int>, "content": [block] }
block  = { "type": <str>, "id": <32 位 hex>, "attrs": {...}, "content": [node]? }
text   = { "type": "text", "text": <str>, "marks": [{ "type": <str>, "attrs": {...} }]? }
```

形状刻意与 ProseMirror 的文档 JSON 一致：前端库与 Python 走**同一份 JSON**，
中间不加转换层 —— 转换层是 bug 的温床，而且转换本身无测试可依。

### 4.2 第一切片的节点清单

| 类 | 成员 |
| --- | --- |
| 块 | `paragraph`、`heading`（level 1–3）、`bullet_list`、`ordered_list`、`list_item`、`quote`（§九）、`code_block`、`divider`、`table` / `table_row` / `table_cell`（§4.7）、`image`、`attachment`、`doc_ref`（§十） |
| 标记 | `strong`、`em`、`strike`、`code`、`link`（§十三）、`highlight`（§十二） |

清单是**封闭**的：不在表里的输入一律在边界被清洗掉（§十五），不是静默保留。

### 4.3 节点身份（A4）

- 块 id = `uuid.uuid7().hex`（32 字符）。选 uuid7 而不是 uuid4 的理由：**时间有序**，
  同一次插入的块在索引与渲染里有稳定顺序，B 树局部性好；且是标准库
  （已在本机 Python 3.14.8 实测 `uuid.uuid7()` 可用），不引 ULID 之类的依赖。
- **行内节点不带 id。** 字级 id 会随每次输入产生与销毁，污染撤销栈、放大体积，
  且行内节点本来就随文本编辑频繁重组。跨版本稳定的行内坐标由 §五 的三段式锚点解决。
- **复制块 = 新 id。** 因此批注与引用不会跟着复制走 —— 这是正确行为，不是缺陷：
  复制一段文字是把内容带走，不是把「对原文的评论」带走。

### 4.4 序列化与版本（不变量 I4）

- 文档 JSON 顶层**必须**带 `version`（整数，当前 `1`）。
- 迁移链是一组**纯函数** `migrate_N_to_M(doc) -> doc` 加一张注册表：
  纯函数无网络、无时钟、无随机，才能被 conformance 覆盖（I4 要求「每个已注册文档
  类型都能从最低版本迁到当前版本」）。
- 非法文档在边界被拒（`ErrKind.INVALID`），**不落库**。库里的每一行都必须是通过校验的。
- **注意两个不同的「版本」**（这是最容易混的一处）：

| 名字 | 是什么 | 归谁 |
| --- | --- | --- |
| `doc.version` | **格式版本**，改格式时 +1，带迁移链（I4） | 本文 §4.4 |
| `revision` | **修订**，用户可见的提交点历史 | §六，保留策略归 025 |

### 4.5 schema 作为资源

`doc.schema.json` 描述节点类型、允许的子节点、属性与标记白名单。两份用途、一份数据：
Python 校验器读它，前端生成器读它。schema 的改动与 DDL 同性质：
**改 schema 就必须同时给迁移**，否则老文档打不开（I4 的意图）。

**打包必须带上它（落地前置，不是可选项）。** `script/build_sidecar.py` 目前只
`rglob("*.sql")` 收集数据文件（`script/build_sidecar.py:90`），所以一个 `.json` 资源
**不会自动进冻结产物** —— 那正是 storage.md §五 说的「开发时能跑、装完就炸」。
落地时必须同时做两件事：把 schema 纳入该脚本的数据发现范围，
并让 `--self-check` **在冻结产物内**断言它可读（与 `.sql` 同一标准）。

### 4.6 块的视觉约束（具体值随 094 组件样式落）

本文件不定义像素，只定结构性约束，其余归 [ui.md](ui.md) §四 的令牌与 4px 网格：

- **层级用边界与内缩表达，不用背景色块**：引用块取左边界线 + 内缩；
- 引用块的左边界线**承载结构信息**，因此按 ui.md §7.1 取 ≥3:1 的
  `--lr-border-strong`，不用纯装饰的 `--lr-border`；
- 高亮用 `--lr-accent-subtle` 作底、文字仍取 `--lr-text`；**该组合的对比度尚未实算**，
  落地前必须按 ui.md §7.1（对三个层级底取最差）补验，不达 4.5:1 就换值（§二十二）；
- 组件内不得出现十六进制字面量（ui.md §八）。

### 4.7 表格（r116）

<a id="r116"></a>

- 三个节点：`table` → `table_row` → `table_cell`。`table` 带列宽（存**比例**不存像素，
  窗口缩放时不失真）；`table_cell` 带 `header: bool`——表头是单元格的属性，
  不靠"第一行特殊对待"，因为表格可以从中间插入表头。
- **单元格内容是行内节点**：不嵌块、**不嵌表格**。允许嵌套就等于允许无限深度，
  锚点、查找替换、粘贴映射、导出、将来的文字级权限全都要跟着处理递归。
- **不做合并单元格**（`colspan` / `rowspan`）。理由：合并让「第 N 行第 M 列」这个坐标失效，
  而单元格坐标是批注锚点、粘贴映射、导出 Markdown 三处的公共依赖；要支持合并，
  就得先把这三处全改成区间模型——成本远大于收益。
- **粘贴 HTML 表格**：尽力映射成行列；遇到合并单元格**拆开并保留文字**（不静默丢内容），
  并提示「合并单元格已展开」。
- **导出 Markdown**：GFM 表格；缺表头时补一行空表头（Markdown 表格语法要求表头行）。
- 批注 / 高亮 / 链接在单元格内照常工作：锚点的 `block_id` 就是 `table_cell` 的 id，
  `offset` 是该单元格的纯文本偏移——§五 的坐标模型不需要为表格改一个字。

## 五、锚点：批注与文字级权限共用的坐标

**三段式锚点**，这是全文最关键的一处数据结构：

```
anchor = { block_id, offset, length, quote, prefix, suffix }
```

- `offset` / `length` 是**块内纯文本**的偏移 —— 不含任何标记语法。这是唯一跨表示稳定的坐标。
- `quote` 是被锚定的原文（截断上限与空白归一化规则见 §二十二）。
- `prefix` / `suffix` 是前后各若干字，用于多命中时消歧。

**重定位算法**（顺序固定，可测）：

1. **快路径**：`block_id` 存在，且该块纯文本在 `offset` 处的 `length` 个字等于 `quote` → 命中。
2. **慢路径**：块内搜索 `quote`；唯一命中即可用；多命中用 `prefix` / `suffix` 消歧。
3. **失败** → 状态置 `orphaned`（待重定位），在检视器里显式列出，**绝不静默丢弃**。
   这与 storage.md §四「行在、本体丢 → 显式报错，不静默给空」是同一条口径。

**块被删**时锚点进入 `orphaned`；**块被复制**时锚点仍指原块（§4.3）。

## 六、提交点：修订从哪来

- **写入分两档，别混**（这是库不膨胀、脊柱不被噪声灌满的关键，A13）：

| 档 | 触发 | 落什么 | 产生修订？ |
| --- | --- | --- | --- |
| **自动落盘** | 空闲节流（默认 3s 无输入）＋ 失焦 | 当前文档行 + 事件日志（I5）+ 增量索引 | **否** |
| **显式提交** | 用户保存（快捷键 / 关闭前）＋ 自动落盘累计到阈值 | 再写一条修订快照 | **是** |

  一次编辑会话里自动落盘会有几十次，修订只该有几个 —— 否则 `doc_revision` 与
  ui.md §3.2 的日志脊柱都会变成噪声。
- **每次写入都带 `base_revision`**（乐观并发）：不匹配返回 `Err(CONFLICT)`
  （`ErrKind.CONFLICT` 已在 contracts.py），前端重取最新修订并**保留本地工作副本让用户决定**。
  **不做自动合并** —— 当前是单用户单窗口，自动合并是给不存在的场景写代码。
- **协作与多用户不阻塞本文**（项目所有者 2026-10-17 裁定）：那是数据侧的权限问题，
  编辑器不为其设计机制，只保证 `Subject` 承载（I6）与提交点是单调的。
- **一次提交 = 一个修订**（`revision` 单调 +1），事务内顺序固定：

```
core.change("doc.saved", …)  →
    1. 事件日志（I5：先写日志）
    2. 文档本体
    3. 修订快照
    4. 反链索引（§十）
    5. 附件引用计数（§十七）
    6. FTS 索引
```

- **撤销 ≠ 修订**：撤销回到提交点之前，不会删除已提交的修订。数据只增不减（I5 的口径），
  「不想要了」由修订历史与未来的回收（044）处理，不由撤销处理。

## 七、撤销与重做（r033）

<a id="r033"></a>

- **建在 step / 事务层**（ProseMirror 事务），不用 `contenteditable` 原生 undo：
  原生栈记录的是 DOM 操作，一次结构化块插入在它眼里是多次操作，撤不回来；
  模型层的 step 才能保证「一次块插入 = 一步撤销」。
- 撤销栈**只在会话内**，不落库、不进事件日志：它不是状态变更的权威来源（那是 §六 的提交点）。
- **输入合并窗口**（默认 500ms）：连续输入合并成一个撤销单元，否则撤销一字一字退；
  遇到结构变更（换块、插块、粘贴）立即断开。
- **输入法（IME）组合期间不打断事务**：组合中的文本按一个单元提交，
  组合中间态不得落盘，否则中文用户每打一个词就产生一个半截修订。

## 八、编辑面与入口

### 8.1 所见即所得编辑面（r109）

<a id="r109"></a>

- **直接编辑**：光标落在正文上就能写，没有「编辑模式 / 预览模式」的切换；
  读面与编辑面是同一处的两种状态（ui.md §3.1 读面，正文 `max-width: 58ch`）。
- **不提供 Markdown 源码视图作为主路径**（§2.2）。
- 工具栏三条入口（§8.3）与快捷键并存，全部键盘可达（ui.md §7.2）。

### 8.2 块插入（r030）

<a id="r030"></a>

- 两个入口：块首的 `+` 手柄，与行首输入 `/` 的块命令；
- 插入清单就是 §4.2 的块清单，**封闭**；
- 插入的块**当场拿到 id**（§4.3），所以插入后立刻可以加批注、被引用。

### 8.3 工具栏（r032）

<a id="r032"></a>

- 选中文字 → **浮动工具栏**（就近出现，不抢正文）；块首手柄 → 块菜单；`/` → 块命令；
- 工具栏**只列当前可用的项**，不做「灰一片」；
- 焦点环、六状态、24×24 最小点击目标按 ui.md §4.2 / §7.3 走。

### 8.4 文本样式与字体（r031）

<a id="r031"></a>

- 提供的是**语义样式**：`strong` / `em` / `strike` / `code` / `link` / `highlight`；
- **不提供 typeface、字号、文字颜色选择**（A8）。理由：ui.md §一「一个强调色、
  安静优先于表达」、§八「组件内不得出现十六进制字面量」、§十 待裁 1（正文衬线未定）。
  放开字体与颜色，等于允许用户把笔记做成海报，也让主题包（098）无法整体换皮。
- 因此「字体支持」这条的落点是**样式语义化 ＋ 字体归主题**：字体由
  ui.md §五 的主题机制与 098 主题包决定，不由单篇文档决定。

## 九、引用块（r110）

<a id="r110"></a>

- 一个块节点 `quote`，attrs：`attribution?`（出处文本，可为空）；
- 内容可以是段落与列表；视觉按 §4.6 的结构性约束；
- 它是**内容**：不指向任何内部笔记。指向内部笔记是 §十，两者刻意分开 ——
  合并成一个节点会让「摘一段外部文章」和「引用我自己的另一篇笔记」共用一套语义，
  而它们的数据、索引、失效行为完全不同。

## 十、笔记引用与反向链接（r111）

<a id="r111"></a>

- 节点 `doc_ref`，attrs：`{ doc_id, block_id?, display: "inline" | "title" | "quote" }`；
  `display: "quote"` 才展开目标块的内容（嵌入），其余只显示行内提及或标题。
  （节点名是 `doc_ref`：引用按**文档**寻址，不按"笔记"——画布类文档同样能引用别的文档。）
- **反链索引**由 Python 在提交事务内维护（§六）：`doc_ref_index(target_doc_id,
  source_doc_id, source_block_id)`。查询走索引，不做全库扫描；
  且只在**本篇引用集变化时**更新（§3.3 第 4 条）。
- **只做一层反链**，不做传递闭包：A 引用 B、B 引用 C 时，A 不会出现在 C 的反链里。
  传递反链会让「谁提到了我」变成不可解释的噪声。
- **读取目标走独立能力** `doc.get`，不在渲染层直接取数据。这样将来权限
  （018/021）天然能在这一层拦下 —— 权限不是靠「渲染时过滤」实现的。
- **悬空引用**（目标已删或不存在）显式呈现为「悬空引用」，可从检视器跳转或修复；
  不静默消失、不降级成普通文本。
- **循环嵌入**（A 嵌 B、B 嵌 A）渲染深度上限 2，超出显示「已折叠：循环引用」。
- **已落（2026-10-17）**：`doc_ref_index` 表 + `doc.refs.backlinks` / `doc.refs.outgoing`
  两个能力；索引只在**引用集变化**时重写（`RefIndex.replace` 会告诉你变没变）；
  来源文档已删的行不出现在反链里，悬空目标由 `outgoing` 的 `exists: false` 显式给出。

## 十一、批注（r112）

<a id="r112"></a>

- 批注是**文档外**的实体：`annotation(id, doc_id, anchor, body, status, author_subject,
  created_wall, updated_wall)`；锚点是 §五 的三段式。
- `status ∈ {active, orphaned, resolved}`：**没有 deleted**。删除是真删行；
  重定位失败是 `orphaned`，不删。
- 位置：ui.md §3.1 的**检视器**（232px，默认展开）承载批注列表；正文内以标记点呈现，
  点开跳到检视器。
- 因为它在文档外：**不经撤销回退**（撤销一次编辑不会撤销一条批注）、
  **不随文档复制而复制**、**可跨多个修订存活**。
- 作者来自 `Subject`（不变量 I6），界面不自行造身份概念（ui.md §九）。
- **已落（2026-10-17）**：`annotation` 表 + `list` / `create` / `update` / `resolve`；
  锚点在**保存事务内**对一遍（`resolved` 的跳过），顺序是快路径 → 慢路径 → 前后文消歧 →
  `orphaned`；`orphaned` **保留原偏移**，正文改回来它能自己恢复。
  **删除批注没有单独能力**：删除是界面上的真删行，随 109 一起落（§十一 的「没有 deleted」说的是状态机）。

## 十二、高亮（r113）

<a id="r113"></a>

- 高亮是**文档内**的标记：`highlight`，可选 attrs `{ annotation_id? }`。
- 因为它在文档内：随文档走、随撤销回退、复制时跟着复制、
  **导出 Markdown 时会丢失**（导出 HTML 时保留，§十五）。
- 与批注的关系：高亮可以没有批注，批注可以没有高亮，两者不互为前提；
  有关联时，**以批注的锚点为权威**（高亮只是它的可见载体）。
- 颜色不可选（ui.md 只有一条强调色轴）：按 §4.6 用 `--lr-accent-subtle` 作底。

## 十三、超链接与零网络（r029）

<a id="r029"></a>

- 链接是标记 `link`，但**内链与外链分开存**：
  外链 `{ href }`，内链 `{ doc_id, block_id? }`。理由：外链需要 I9 的显式用户动作，
  内链不需要，而且内链要参与反链索引（§十）。
- **渲染期零网络**（A9）：

| 输入 | 处置 |
| --- | --- |
| 远程图片 `<img src="https://…">` | 必须**本地化**成附件（107）才显示；失败则保留原文链接文本 + 显式提示 |
| 远程字体 / 样式 / iframe | 一律不加载、不保留 |
| 悬停外链 | **不预取**、不预览 |
| 点击外链 | 用户显式动作 → 交宿主用系统浏览器打开（I9 允许：由用户发起） |

- 这条直接否决了富文本编辑器的默认行为（很多编辑器渲染时就拉远程图片），
  它们在本项目等于「打开笔记就联网」。

## 十四、查找替换（r034）

<a id="r034"></a>

- **模型级查找**，不是 DOM 查找：在文档树的纯文本上匹配，命中转成 ranges 后高亮呈现
  （复用 §十二 的视觉，但**不写入文档**）。
- 替换是**一次事务**（可撤销）；「全部替换」先在客户端算好新文档并整体校验，
  校验不过就整体拒绝，不做「替换一半」。
- 范围是**当前笔记**。跨笔记查找属于检索（FTS5，storage.md §三），不是本条。

## 十五、粘贴、导入导出

- **粘贴是最常发生、也最脏的入口**（普通用户的工作流就是从网页/Word 里粘）。
  两道都要有：**前端 paste rules 做第一道清洗**（丢 script/style/远程资源/内联色与字号），
  **Python 在提交时按 schema 做第二道校验**（权威）。只做一道都不够：
  只做前端，前端有 bug 就入库；只做后端，用户会看到满屏拒绝。
- **保留**：段落、标题、列表、加粗/斜体。**丢弃**：字体、颜色、字号、外链样式表。
- **导入**：Markdown → 文档树，尽力映射；不支持的语法落成 `code_block` 或原始文本，
  **不静默丢弃**，导入后给一份映射报告。
- **导出**：文档树 → Markdown（有损：批注、高亮、笔记引用的展开形态降级）、
  纯文本、HTML（保留高亮与内链）。**导出前显式告知损失**。
- **为什么 Markdown 只能在边界**：它没有节点身份、没有 `version` 字段、
  文本偏移随编辑漂移 —— 把它当存储就是把 A1/A4/A7 与文字级权限全部作废。

## 十六、与权限的接口预留

- 文字级权限（018）需要的范围坐标就是 §五 的锚点：未来 `guard(subject, action, obj)`
  的 `obj` 可携带块 id 与范围。**本文件不设计权限语义**，只保证坐标稳定、可序列化、可重定位。
- 编辑器的每个跨模块动作都走总线调用平面、都带 `Subject`（I6，bus.md §六）。
- 当前 `guard` 未装配 → 总线 `_decide` 直接返回 `ALLOW`（`src/lurnia/core/bus.py`）。
  **这不是本文要解决的事**，但它意味着「今天没有权限」是**显式状态**，不是被绕过。
  权限模块（012–028）与它依赖的多用户/网络前提另行处置。

## 十七、文档存储（r114）

<a id="r114"></a>

**存的是「文档」，不是「笔记」**（A15）：所有编辑器种类共用一套表与一套能力，类型由
`doc_type` 判别。加一种编辑器是**注册一个类型**（§3.1）——不加表、不加列。

- **schema 名 `doc`**，DDL 落 `src/lurnia/components/doc/sql/doc/{tables,migrations}/*.sql`
  —— **业务 schema 归组件包，不进 `core/`**（storage.md §五，2026-10-17 修订）。
  组件在装配时自己声明这件事：`ddl.register_schema("doc", __package__)`，
  所以内核不需要认识任何业务名。这样加业务数据结构时 diff 落在组件目录，内核零改动；
  `core/sql/kernel/` 里只留内核自己的 `event_log`、`attachment`。
  **不要往仓根 `config/` 放**：它在包外，冻结产物里没有它——`tests/test_ddl.py` 有一条
  专门拦这件事的测试，放进去当场红。
  `script/audit.py` 的 `schema_drift_violations()` **已改成扫两处根**（内核 + 组件），
  否则新根下的 schema 会丢掉 I4 的「快照 vs 迁移链」防线。
- 表（`doc` / `doc_revision` 是切片 0，`annotation` / `doc_ref_index` 随 111、112 落地，
  schema `doc` 现在是 **v2**；`doc_fts` 见下）：

| 表 | 装什么 | 状态 |
| --- | --- | --- |
| `doc` | `id` / `doc_type`（`note`、将来的画布等）/ `title` / `body`（§4 的 JSON）/ `body_version` / `revision` / 时间戳 | **已落** |

**只有 `doc_type` 与 `title` 是列**：前者是判别式，后者是唯一真正通用的字段（要排序、要列表）。
凡是"某种编辑器才有的东西"，一律进 `body` 或 `attrs` 的 JSON —— 这就是「加编辑器不改库」的
机械保证（storage.md §八）。

> **全文索引的归属（2026-10-17 改判）。** 它一度被写进本文档 schema，现在移出：
> 它是**派生数据**（storage.md §八），该有自己的 schema 与版本链，好让"重建索引"是
> 一次 DROP 重建而不是文档 schema 的一次迁移。搜索是独立能力（跨类型、只读、
> 有自己的排序与分词问题），路线号 **118**。
>
> **`doc_fts` 为什么没做（2026-10-17 实测）。** FTS5 的默认分词器 `unicode61` 把没有空格的
> 中文整段当一个 token，`MATCH '中文检索'` 返回 **0 条**；`trigram` 能用，但两字词仍搜不到
> （详见 [storage.md §三](storage.md) 的更正表）。**中文分词口径没定之前不建 FTS 表**：
> 建了就是「装完才发现搜不到」。口径见 §二十二 未决。

- **body JSON 走数据库**：它是结构化数据，要参与事务。storage.md §二 的 100KB
  阈值只对**二进制附件**，不适用于正文。
- **不 re-dump**：前端发来的 JSON 文本，校验通过后**原样入库**（§3.3 第 2 条）——
  所以 `doc.save` 的 `body` 是 **JSON 文本**，不是对象（见下表）。
  超出单篇上限（8 MiB）直接 `Err(INVALID)`，不截断。
- **附件引用计数**：插入 +1、移除 −1，归零才真删（107 的口径）；计数变更与文档写入
  **同一事务**（否则会留下指向已删附件或永不回收的孤儿）。
- **谁执行**：组件启动时 `db.ensure("doc")` —— `open_db` 已按 schema 分键
  （`schema_meta` 记名），两条链各自从 0 起步。
- **能力**（每条恰好一个提供者，bus.md §三；名字里**没有"笔记"**，所以画布与设计器也能用。
  全部已落）：

| 能力 | 请求 → 回复 | 状态 |
| --- | --- | --- |
| `doc.get` | `{doc_id}` → `{doc_type, title, body, body_version, revision}` | **已落** |
| `doc.save` | `{doc_id, body: <JSON 文本>, base_revision, commit, title?}` → `{revision}`／`Err(CONFLICT)` | **已落** |
| `doc.annotation.list` / `create` / `update` / `resolve` | 批注的增改查（§十一） | **已落** |
| `doc.refs.backlinks` | `{doc_id}` → `[{source_doc_id, source_block_id, source_doc_type, title}]`（§十） | **已落** |
| `doc.refs.outgoing` | `{doc_id}` → `[{target_doc_id, source_block_id, exists, title}]`（悬空引用显式呈现，§十） | **已落** |

  两条写入语义已在实现里钉住：**`commit` 缺省为假**（自动落盘只更新当前行，
  `revision` 不动），**`commit: true` 才 +1 并写一条 `doc_revision`**（§六 两档写入，
  A13）；`base_revision` 不匹配一律 `CONFLICT`，不自动合并。
  `title` 不给就由类型抽取器从正文派生（§3.2 第 3 条）。

- **性能与稳定性口径**（所有者 2026-10-17 的硬要求：快、稳、通用，不要三天两头改库；
  数字见 §3.3 的实测）：
  - **启动零扫描**：打开文档是按主键读一行；反链与 FTS 增量维护，**不在打开时重算**；
  - **保存不 re-dump**：前端发来的 JSON，校验通过后**原样入库**（§3.3 第 2 条）；
  - **FTS 只在提交点更新**（A17）：实测它占保存开销的八成（2 MB 文档 40 ms，整条 51 ms），
    所以自动落盘不碰它；检索**最终一致**，落后最多一个提交点；
  - **反链只在本篇引用集变化时更新**（§3.3 第 4 条）；
  - **派生数据可重建**：FTS、反链、引用计数都属于"能从权威重算"的一类，所以它们的表结构
    改动不算破坏性变更（storage.md §八）——这是「不用频繁迁移」的主要来源；
  - **文档体积**：单文档硬上限暂定 8 MiB（超了返回 `Err(INVALID)` 并明示），
    1 MiB 只告警（§二十二）；
  - **修订不因节流膨胀**：见 §六 的两档写入。
- **与 025 版本控制的边界**：**存储与写入顺序**归本条；**保留策略、差异呈现、回退口径**
  归 025（另一篇设计）。本文只保证「提交点」这个概念存在且单调。

## 十八、前端调用通道（r115，口径在 [packaging.md](packaging.md) §五）

**现状（已核实，不是推测）**：`app/src/kernel.ts` 只有 `listen`，没有调用；
`src/lurnia/sidecar.py` 明说「**stdin 不解析**」，只等 EOF；`app/src-tauri/src/lib.rs`
只把 stdout 的行转发成前端事件。也就是说 **宿主 → 内核这条路今天不存在**：
前端能看事件，不能请求。

编辑器是第一个**必须请求**的组件（存/取笔记、拉反链），所以这条路必须先在：

| 侧 | 改动 |
| --- | --- |
| 协议 | stdio 行协议加 `call` / `reply` 两种帧，协议号 v1 → **v2**（帧格式落在 packaging.md §五） |
| Python | `sidecar.py` 开始读 stdin（EOF 仍退出）；`call` 走 `bus.invoke`，回复用 `Ok` / `Err` 共享错误模型 |
| 宿主 | `lib.rs` 加一个 `#[tauri::command]`，把前端 `invoke()` 转到 sidecar stdin，并按 id 关联回复 |
| 前端 | `kernel.ts` 加 `callKernel()` |

- **不把调用塞进事件帧**：调用平面「恰好一个提供者、没人接必须报错」，广播平面
  「尽力而为、允许没人接」（bus.md §一）。合成一条会让「没人接」不可区分 ——
  那正是 bus.md 拒绝合并两个平面的理由。
- **`subject` 由内核填本机主体**，前端不传、不造身份（ui.md §九）。I6 在边界外仍然成立。
- **协议升到 v2 是干净升级**：本项目 0.1.0、未发布，不做双版本兼容；实现时把
  `protocol` 常量一起升到 2（`ready` 帧里的 `protocol` 字段就是这个号）。

## 十九、技术选型（A10）

- **选 ProseMirror**：schema（对应 A3 的单一来源）、事务 / step（对应 §七 撤销与将来的

   > 直接扫，替换是一次可撤销的事务（§十四）。所以这条未决**不挡 034，也不挡 109**，
